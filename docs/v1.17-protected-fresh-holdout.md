# ATMAN-CONFIRM/1.17 — Protected Fresh Holdout Rotation

v1.17 adds a protected final-confirmation plane after v1.16 finite-search structural selection.

The goal is not another search score. The goal is to keep one final dataset outside model search and expose it exactly once to one already-selected model.

```text
DISCOVERY / TRAINING
        |
v1.15 held-out validation
        |
v1.16 finite-search correction
        |
selected candidate + independent review
        |
        v
sealed fresh confirmation batch
        |
one-shot exposure authorization
        |
final confirmation evaluation
        |
independent confirmation review
        |
confirmed apply
```


## Freshness is provenance, not partitioning

v1.15 deterministically split one historical dataset into selection and held-out evaluation partitions. v1.16 limited repeated access to that held-out surface.

v1.17 deliberately does **not** create a third bucket from the same history.

A protected confirmation batch is stored in a separate table and must be disjoint from search history by:

```text
sample_hash
resolution_hash
left_evidence_hash
right_evidence_hash
```

It must also be disjoint from all prior protected confirmation batches for the same subject/pair.

Therefore:

```text
NewSplit != FreshEvidence
NewBatchName != NewEvidence
RepartitionedOldData != FreshHoldout
```

This catches aliasing where a caller recomputes a new sample hash around an already-resolved event or re-derives the same evidence through a different wrapper.

## Sealed batches

`ProtectedConfirmationBatch` binds:

```text
batch_ref
subject_identity_ref
pair_key
source_ref
sample_hashes
resolution_hashes
evidence_hashes
sample_count
batch_keeper_ref
sealed_at
batch_hash
```

The batch is immutable after sealing.

The reference runtime keeps full sample JSON in a confirmation-only table. Search and structural workers have no protocol operation that enumerates these samples.

This is a logical/process boundary, not a hostile-host secrecy guarantee. Production use requires protected storage, access control, audit logging, and leakage-resistant data handling.

## One-shot exposure

`ConfirmationExposureReceipt` binds one exact:

```text
v1.16 selection
selected candidate
v1.16 review
confirmation batch
confirmation policy
search history
base graph
```

A selection may receive at most one confirmation exposure.

A batch may be exposed to at most one selection.

Therefore a failed final check cannot be followed by repeatedly opening fresh final batches for the same already-selected candidate until one passes.

```text
OneSelection -> AtMostOneConfirmationExposure
OneBatch -> AtMostOneSelection
```

## Confirmation scoring

Confirmation does not refit on confirmation samples.

The selected candidate's selection/training sample hashes remain the training set. The protected batch is score-only.

For the candidate direction, the runtime computes base and proposed positive predictions from the bound search-selection training data, then evaluates Brier score on the confirmation samples.

The same structural edge penalty from v1.15 is retained:

```text
base_regularized = base_mean_brier + edge_penalty * base_edges
proposed_regularized = proposed_mean_brier + edge_penalty * proposed_edges
regularized_improvement = base_regularized - proposed_regularized
```

Confirmation policy adds a final minimum required regularized improvement.

Statuses:

```text
INSUFFICIENT_CONFIRMATION
CONFIRMATION_REJECTED
CONFIRMED
```

`CONFIRMED` requires:

```text
scored_count >= min_confirmation_samples
regularized_improvement > min_regularized_improvement_ppm
```

## Confirmation is not truth or causality

The underlying graph relation remains:

```text
STATISTICAL_CONDITIONING
```

A successful final confirmation means the selected structure generalized better under the exact protected confirmation procedure.

It does not prove a physical causal mechanism, universal generalization, or ontological truth.

```text
CONFIRMED != ProvenCausality
Confirmation != Truth
```

## Use-time freshness

Before evaluation and again before apply, the runtime reconstructs current v1.16 search selection state.

If new search evidence, a new reserved candidate, a changed winner, or a changed base graph makes the old v1.16 selection stale, confirmation can no longer authorize mutation.

The runtime also rechecks that the sealed confirmation provenance has not appeared in search history since sealing.

```text
OldSearchSelection != CurrentConfirmationAuthority
LaterLeakage != ProtectedHoldout
```

## Authority separation

v1.17 adds:

```text
CONFIRMATION_POLICY_KEEPER
CONFIRMATION_BATCH_KEEPER
CONFIRMATION_EXPOSURE_KEEPER
CONFIRMATION_EVALUATOR
CONFIRMATION_REVIEWER
CONFIRMED_STRUCTURAL_APPLIER
```

The reference core enforces key separations:

```text
candidate proposer != batch keeper
search selector != batch keeper
exposure keeper != proposer / selector / batch keeper
evaluator != proposer / selector / batch keeper / exposure keeper
reviewer != proposer / selector / evaluator
CONFIRMED != APPLIED
```

## Durable state

SQLite stores separately:

```text
protected confirmation policy
sealed batches and sample JSON
one-shot exposures
confirmation evaluations and cases
confirmation reviews
confirmed old/new graph revision history
```

All mutation operations execute under `BEGIN IMMEDIATE` in the reference worker path.

## Compatibility boundary

v1.17 is the stronger structural-apply path. Existing v1.16 receipts remain valid historical objects. Installing and using the confirmation plane does not rewrite v1.15/v1.16 evidence or selections.

The reference implementation remains a formal/process/database boundary. It is not a cryptographic data-room, a hostile-host sandbox, a p-value engine, or a causal-identification proof system.
