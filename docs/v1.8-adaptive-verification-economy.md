# v1.8 — Adaptive Verification Economy

v1.8 adds an economic layer in front of finite-capacity verification.

The purpose is not to price truth. The purpose is to allocate a finite verification budget without trusting a submitter's claimed verification cost.

## Four distinct statements

```text
Declared cost   = submitter/work estimate
Observed cost   = authenticated accounting observation
Funding         = budget allocated for verification
Verification    = evidence-producing work completed
Truth/coherence = semantic decision after verification
```

Therefore:

```text
DeclaredCost != AccountingCost
Funding != Verification
Verification != Automatic PASS
Funding != Truth
```

## Plane separation

```text
ATMAN-RUNTIME/1.1  privileged execution
ATMAN-TRUST/1.2    trust governance
ATMAN-VERIFY/1.7   verification debt / completion / finalization
ATMAN-ECONOMY/1.8  adaptive verification-budget allocation
```

`ATMAN-ECONOMY/1.8` does not rewrite A3/A4 verdicts. It decides only which pending verification candidates receive budget in the current allocation.

## Candidate contract

`EconomicVerificationCandidate` binds:

```text
existing v1.7 work_hash
subject identity
estimator class/key
declared cost copied from the existing work item
value units
risk units
priority
submission time
candidate hash
```

The economy runtime requires an existing `verification_work` row. A caller cannot create economic work that has no corresponding verification debt.

The declared cost is preserved as provenance, but the adaptive allocator does not use it as the accounting cost.

## Cost observations

A completed verification may receive one `CostObservationReceipt`:

```text
work_hash
completion_hash
estimator_key
observed_cost_units
measured_at
meter_ref
observation_hash
```

The runtime requires:

1. the work already exists;
2. the work has an actual v1.7 completion receipt;
3. the cost observation is bound to that exact completion hash;
4. the observation estimator key matches the candidate estimator key;
5. the action is authorized by `VERIFICATION_COST_METER`;
6. the meter identity is taken from the authority grant, not a caller-provided display field;
7. at most one cost observation exists for one exact work hash.

This prevents the submitter from making a cheap claim and automatically turning it into accounting truth.

### Reference-boundary limitation

The research runtime does **not** automatically measure CPU cycles, wall-clock time, accelerator use, API spend, or energy. `observed_cost_units` is an authenticated accounting measurement supplied by an authorized meter. A production deployment should bind the meter to protected operating-system counters, tool billing receipts, compute telemetry, or another independently auditable resource source.

## Cost estimator

For each `estimator_key`, observations produce a `CostEstimatorSnapshot`:

```text
sample_count
total_observed_cost
ceiling arithmetic mean
exact observation hashes
snapshot hash
```

For a candidate:

```text
if no observations:
    estimated cost = bootstrap cost + uncertainty premium

if observations exist but sample_count < confidence threshold:
    estimated cost = observed mean + uncertainty premium

if sample_count >= confidence threshold:
    estimated cost = observed mean
```

This gives new classes a conservative bootstrap without accepting the candidate's declared cost as truth.

## Allocation utility

The reference ranking uses an integer utility:

```text
utility =
    value * value_weight
  + risk * risk_weight
  + priority * priority_weight
  + floor(wait_time / aging_quantum)
```

and ranks by utility per estimated cost, with deterministic tie-breaking.

Aging makes old verification debt progressively more competitive. This is an anti-starvation mechanism, not a guarantee that a work item whose estimated cost exceeds the whole budget can ever fit.

## Budget dispositions

Every candidate must occur exactly once in:

```text
FUNDED
DEFERRED_BUDGET
DEFERRED_OVERSIZED
```

No candidate may silently disappear.

```text
NORMAL     -> every candidate funded
PRESSURED  -> some funded, some deferred
SATURATED  -> no candidate can be funded now
```

As in v1.6:

```text
Deferred != Invalid
Deferred != Pruned
```

## Runtime persistence and stale-state protection

The economy process persists:

```text
verification_economy_candidate
verification_cost_observation
verification_budget_allocation
```

A preview returns:

```text
state_hash
allocation
current allocation generation
```

Finalization requires `VERIFICATION_BUDGET_KEEPER` authority over the exact:

```text
state_hash
allocation_hash
policy_hash
next generation
runtime finalization time
```

Before commit, the worker rebuilds current candidate/estimator state. If it differs from the preview state:

```text
OldEconomicPreview != CurrentBudgetAuthority
```

and finalization is rejected.

## Authority roles

```text
VERIFICATION_ECONOMY_SUBMITTER
    -> binds value/risk metadata to existing verification work

VERIFICATION_COST_METER
    -> records one completion-bound observed cost

VERIFICATION_BUDGET_KEEPER
    -> finalizes the current budget allocation
```

These roles do not grant verification-executor or verification-finalizer authority.

## Central rule

The economic plane decides where scarce verification attention goes.

It does not decide what reality is.

```text
Finite attention requires allocation.
Allocation requires evidence about cost.
Cost evidence must not become semantic authority.
```
