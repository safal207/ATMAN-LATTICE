# v1.7 — Runtime Verification Plane

v1.7 moves the v1.5 geometric coherence gate and v1.6 verification-pressure semantics behind a durable process/database boundary.

This is a reference verification plane for agent systems. It is not a hostile-host sandbox and does not claim physical torsion/multiverse semantics.

## Three protocol planes

```text
ATMAN-RUNTIME/1.1  privileged execution
ATMAN-TRUST/1.2    trust-root governance
ATMAN-VERIFY/1.7   verification debt, admission, completion, finalization
```

The verification worker is launched separately:

```bash
python -m model.verification_worker
```

## Runtime lifecycle

```text
A3/A4 geometric gate
        |
        v

        |
        v

        |
        v

        |
   schedule window

  |       |          |

  |

  |

  |

```

## Server-owned facts

Clients do not control:

- runtime clock used for `submitted_at`, scheduling, completion, and finalization;
- verification capacity units;
- maximum admitted item count;
- aging quantum;
- persisted debt state;
- current schedule generation;
- current pressure receipt.

Client-provided capacity-like fields in a schedule request are ignored by the reference worker.

## Durable debt

Verification work is persisted in SQLite with one of these states:

```text
SUBMITTED
ADMITTED
DEFERRED_CAPACITY
DEFERRED_OVERSIZED
COMPLETED
```

A fresh worker process reads the same database, so process restart does not erase deferred work.

The invariant is:

```text
Deferred work is unresolved evidence debt, not invalid evidence and not deleted evidence.
```

## Completion is a verdict, not a checkbox

v1.6 distinguished `ADMITTED` from `VERIFIED`. v1.7 makes completion explicit with `VerificationCompletionReceipt`.

A completion binds:

- exact work hash;
- exact target geometric gate;
- exact schedule generation;
- exact pressure receipt;
- PASS/HOLD/FAIL result;
- evidence digest;
- actor;
- runtime completion time.

Only work currently admitted in the active pressure window may be completed.

Therefore:

```text
COMPLETED != PASS
```

A completed `FAIL` remains a failure and cannot be hidden by complete coverage.

## Discharging geometric HOLD

A geometric `HOLD` means the path is locally meaningful but requires more evidence before global commitment.

v1.7 allows:

```text
base geometry = HOLD
required verification work exists
all required work completed
all completion decisions = PASS
--------------------------------
runtime verification decision = PASS
```

But:

```text
pending/deferred work -> HOLD
any completion HOLD   -> HOLD
any completion FAIL   -> FAIL
base geometry FAIL    -> FAIL
```

A HOLD with no verification work stays HOLD; absence of a queue is not evidence of resolution.

## Preview vs authoritative finalization

`evaluate_geometric_verification` is a preview/read model.

It returns:

- a time-stamped `RuntimeVerificationDecisionReceipt`;
- a stable `decision_state_hash` that excludes observation time.

The stable state digest commits to the actual schedule/debt/completion state. It changes when the meaningful verification state changes, not merely when the clock advances.

To make the decision authoritative, the caller uses `finalize_geometric_verification` with a `VERIFICATION_KEEPER` authority proof over the exact current state.

The finalizer recomputes current state and rejects a stale preview:

```text
preview state S0
verification state changes -> S1
finalize proof for S0
-----------------------
REJECT: stale verification decision
```

This closes the preview-to-finalization TOCTOU window.

## Authority separation

```text
VERIFICATION_SUBMITTER -> may add evidence debt
VERIFICATION_EXECUTOR  -> may record a result for currently admitted work
VERIFICATION_KEEPER    -> may finalize the current runtime verification decision
```

Scheduling itself is deterministic under server-owned policy. Triggering a scheduling pass does not grant authority over the truth of its results.

## Atomicity boundary

SQLite mutations use `BEGIN IMMEDIATE` for queue submission, scheduling disposition changes, and completion writes. This serializes reference-store mutations across separate worker processes.

Production deployments still need protected durable storage, rollback-resistant backups, authenticated transport, protected signer keys, and operational controls.

## Core laws

```text
Unverified != Invalid
Admitted != Verified
Completed != Pass
Deferred != Pruned
Preview != Finalization
Old preview != Current authority
Verifier capacity != Reality capacity
```
