# ATMAN-LATTICE v0.9 — Authority Enforcement

Version 0.9 moves authority from an inspectable proof into the execution path.

The v0.8 rule was:

> A valid signature does not imply valid authority.

The v0.9 rule is stronger:

> Valid authority does not matter unless it is checked before the privileged primitive executes.

## Governed boundary

`model/enforcement.py` is the governed execution boundary.

The pure research primitives remain available in their original modules so that invariants can be tested independently:

```text
model/lattice.py      -> identity / observer primitives
model/freshness.py    -> attestation / token primitives
model/consumption.py  -> authorization-ledger primitives
model/merge.py        -> merge primitive
```

Governed callers use:

```text
model/enforcement.py
```

which performs authority verification first and calls the low-level primitive only after the gate passes.

This separation is deliberate:

```text
mechanism != permission
```

A pure function describes what a transition means. The enforcement layer decides whether a caller may invoke that transition in the governed runtime.

## Role map

Version 0.9 assigns exact operation roles:

```text
observe_space       -> A1_OBSERVER
observe_time        -> A2_OBSERVER
cross_axis_bind     -> A3_BINDER
global_coherence    -> A4_KEEPER
issue_use_token     -> USE_TOKEN_ISSUER
revoke_use_token    -> USE_TOKEN_REVOKER
merge_branches      -> BRANCH_MERGER
```

A grant may contain many roles. That does not permit a proof to select an arbitrary granted role for an operation.

The proof role must equal the role required by the operation.

## Scope map

Observer and merge operations use:

```text
identity:<identity_ref>
```

Authorization lifecycle operations use:

```text
authorization:<identity_ref>
```

A grant may also contain multiple scopes, but the proof scope must equal the exact scope required by the governed operation.

## Exact action binding

Every governed operation reconstructs the action object from the actual runtime inputs before authority verification.

Examples include commitments to:

```text
A1/A2:
  exact input receipt hashes

A3/A4:
  exact observer-receipt digests

issue_use_token:
  observer receipt
  attestation
  current context
  issuance time
  TTL
  token key id

revoke_use_token:
  exact use-token digest
  ledger generation
  expected generation
  actor
  reason
  revocation time

merge_branches:
  ancestor receipt
  both parent heads
  target branch/generation
  merged payload digest
  resolution-set digest
  merge time
```

The Ed25519 `AuthorityProof` must verify against that reconstructed action. A proof for a nearby but different action cannot authorize execution.

## Gate-before-execution property

The execution shape is:

```text
runtime inputs
     |
     v
reconstruct exact action
     |
     v
verify root -> grant -> proof
     |
     +-- role exact?
     +-- scope exact?
     +-- current policy generation?
     +-- grant currently valid?
     +-- exact action digest?
     +-- correct signer key?
     |
     +---- FAIL -> PermissionError
     |
     v
privileged primitive executes
```

The test suite includes a regression where the low-level `observe_space()` primitive is replaced by a function that would explode if called. A proof with a cryptographically valid but wrong granted role is rejected and the primitive is never invoked.

That is the v0.9 distinction between **checking authority around an action** and **enforcing authority before an action**.

## Important boundary

This Python research harness is not an operating-system sandbox.

A caller that deliberately imports and invokes the low-level primitive modules directly can bypass the governed API. Therefore v0.9 proves the enforcement semantics of the `model.enforcement` boundary; it does not claim process isolation against hostile Python code.

A production deployment that requires non-bypassability must place the privileged primitive behind a real isolation boundary such as a service, capability-restricted worker, process boundary, hardware-backed signer, database permission boundary, or equivalent mechanism.

## Result

The authority chain is now:

```text
Trusted Root
    |
    v
AuthorityGrant
    |
    v
AuthorityProof(exact action)
    |
    v
Operation-specific role + scope gate
    |
    v
Privileged primitive
```

So the governing relation becomes:

```text
Authentic signer
+ current grant
+ exact role
+ exact scope
+ exact action
+ current policy generation
= admissible invocation
```

not merely an informative audit record.
