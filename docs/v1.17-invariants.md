# ATMAN-LATTICE v1.17 — Protected Fresh Holdout Invariants

v1.17 adds a one-shot confirmation layer after v1.16 search-budgeted structural selection. Its purpose is to keep final confirmation data outside model search and to distinguish fresh provenance from merely re-partitioned history.

## I-311 — Search Holdout Is Not Confirmation Holdout

Data used by discovery/search cannot simultaneously serve as final confirmation evidence.

`SearchHoldout != ConfirmationHoldout`

## I-312 — New Split Is Not Fresh Evidence

Changing a modulus, salt, bucket assignment, file name, or batch name does not create fresh evidence from previously observed data.

`NewSplit != FreshEvidence`

## I-313 — Repartitioned Old Data Is Not Fresh Holdout

A confirmation batch must be provenance-disjoint from the persisted search history.

## I-314 — Sample Hash Freshness Is Necessary But Not Sufficient

A new `sample_hash` does not establish freshness if the same resolved event or evidence provenance is reused.

## I-315 — Resolution Provenance Cannot Be Reused

A confirmation batch sharing a `resolution_hash` with search history is rejected even when its sample hash differs.

## I-316 — Evidence Provenance Cannot Be Reused

A confirmation batch sharing either side's evidence hash with search history is rejected.

## I-317 — Holdout Rotation Requires New Provenance

A later confirmation batch must be provenance-disjoint from every earlier confirmation batch for the same subject/pair.

`NewBatchName != NewEvidence`

## I-318 — Confirmation Batch Is Sealed Before Exposure

The exact batch hash and sample-provenance set exist before a selected model is authorized to inspect the batch.

## I-319 — Only a Search-Selected Model Can Enter Confirmation

A confirmation exposure binds one exact v1.16 `selection_hash` and its exact selected candidate.

## I-320 — Search Review Precedes Confirmation Exposure

The selected search candidate must already have an independent `APPROVE` review before final confirmation can be opened.

## I-321 — One Selection Gets At Most One Confirmation Exposure

A failed or inconvenient confirmation result cannot be retried against another final holdout under the same exact search selection.

## I-322 — One Confirmation Batch Is Exposed to At Most One Selection

A protected batch cannot become a model-comparison surface by being shown to multiple candidates.

## I-323 — Exposure Keeper Is Independent

The confirmation exposure keeper cannot be the candidate proposer, search selector, or confirmation batch keeper.

## I-324 — Batch Keeper Is Independent From Search Choice

The actor sealing the protected final batch cannot be the selected candidate proposer or search selector.

## I-325 — Confirmation Evaluator Is Independent

The confirmation evaluator cannot be the candidate proposer, search selector, batch keeper, or exposure keeper.

## I-326 — Confirmation Uses Search Training Only

Prediction parameters for the selected structural hypothesis are estimated from the candidate's bound selection/training data. Confirmation samples are scored, not folded back into training before their result is issued.

## I-327 — Confirmation Is a Separate Receipt

Search-adjusted evaluation and protected confirmation evaluation remain separately preserved.

`SearchCorrectedImprovement != ConfirmationResult`

## I-328 — Confirmation Failure Does Not Mean Ontological Falsehood

`CONFIRMATION_REJECTED` means the selected structure failed the bound final-confirmation policy. It is not a proof that the dependency is impossible in reality.

## I-329 — Confirmation Success Is Not Causality Proof

`CONFIRMED != ProvenCausality`

The graph relation remains statistical conditioning.

## I-330 — Confirmation Success Is Not Truth

Passing a fresh final holdout strengthens generalization evidence only.

`Confirmation != Truth`

## I-331 — Search-State Change Stales Confirmation Authority

If search history, candidate set, selected winner, search policy context, or base graph changes after exposure, the old confirmation chain cannot mutate the graph.

## I-332 — Freshness Is Rechecked at Evaluation and Apply

A batch that becomes contaminated by later insertion of its provenance into search history is no longer admissible as protected confirmation.

## I-333 — Confirmation Review Is Independent

The confirmation reviewer cannot be the candidate proposer, search selector, or confirmation evaluator.

## I-334 — CONFIRMED Does Not Apply Itself

A `CONFIRMED` evaluation still requires independent review and a distinct apply authority.

`CONFIRMED != APPLIED`

## I-335 — Old and New Graph State Remain Preserved

Successful confirmed apply stores the complete pre-revision and post-revision graph states together with the search and confirmation chains.

## I-336 — Confirmation Evidence Is Not General Execution Authority

Protected confirmation receipts authorize no tool execution, trust-root mutation, or unrelated state transition beyond their explicit structural revision role.
