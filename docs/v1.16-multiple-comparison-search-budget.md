# ATMAN-LATTICE v1.16 — Multiple-Comparison / Search-Budget Governance

Protocol: `ATMAN-SEARCH/1.16`

v1.16 governs repeated access to the v1.15 held-out structural validation surface. The goal is to stop a fixed evaluation partition from gradually becoming training data through repeated graph search.

This is a finite-search governance layer. It does **not** derive p-values, prove family-wise error rates, or identify physical causality.

## Core problem

A single held-out split is not an infinite oracle.

```text
candidate 1 -> held-out
candidate 2 -> held-out
candidate 3 -> held-out
...
candidate N -> held-out
```

Even when every individual comparison is honest, repeated search against the same control surface leaks information about that surface into model selection.

Therefore:

```text
OneHeldOutSet != InfiniteSelectionBudget
RepeatedEvaluation != FreshEvidence
SearchMultiplicity != Knowledge
```

## Search family

The cumulative search family is bound to:

```text
subject_identity_ref
pair_key
structural_validation_policy_hash
search_budget_policy_hash
```

It intentionally does **not** include the current history hash or graph generation.

Consequently, adding a new dependency sample or advancing the graph does not reset the number of held-out looks already consumed under the same search policy.

## Policy

`HeldOutSearchBudgetPolicy` binds:

```text
max_unique_evaluations
base_min_regularized_improvement_ppm
multiplicity_penalty_ppm
```

For unique evaluation ordinal `n`:

```text
required_improvement_n =
    base_min_regularized_improvement_ppm
    + multiplicity_penalty_ppm * (n - 1)
```

This is an explicit regularization rule, not a statistical-significance theorem.

## Reservation before exposure

A candidate must receive `HeldOutSearchReservation` before evaluation.

The reservation fixes:

```text
candidate_hash
search family
exact structural context
ordinal
remaining policy capacity
effective required improvement
budget keeper
```

The runtime records reservations under `BEGIN IMMEDIATE`, so concurrent processes cannot allocate the same ordinal twice.

An exact candidate can own only one reservation. Re-requesting it returns the same receipt and consumes no additional unit.

## Legacy pre-exposure is not fresh evidence

If the candidate already has a v1.15 `structural_validation_receipt` before v1.16 reservation, the reference runtime rejects it as fresh search-budget evidence.

The control set has already been observed.

```text
AlreadyObserved != FreshHeldOutEvidence
```

## Search-adjusted evaluation

After reservation, a separate evaluator runs the ordinary v1.15 held-out validation and preserves that full receipt.

v1.16 then compares its regularized improvement against the reservation threshold.

Outcomes:

```text
UNDERLYING_HELDOUT_REJECTED
MULTIPLICITY_REJECTED
SEARCH_CORRECTED_IMPROVED
```

So a candidate may truthfully have:

```text
v1.15: HELDOUT_IMPROVED
v1.16: MULTIPLICITY_REJECTED
```

without contradiction.

The first statement concerns one held-out comparison. The second concerns that comparison in the context of prior search exposure.

## Cumulative budget survives model/history changes

Suppose candidate A consumed ordinal 1 under History H0.

Then new evidence creates History H1 and candidate B.

If A and B remain in the same search family:

```text
A -> ordinal 1
B -> ordinal 2
```

not:

```text
A -> ordinal 1
new history
B -> ordinal 1 again
```

This prevents trivial reset-by-new-sample behavior.

## Selection

Search selection uses only candidates in the current structural context, but binds the **entire cumulative family reservation set**.

Every reserved candidate in the current context must already have an evaluation.

Eligible candidates are those with:

```text
SEARCH_CORRECTED_IMPROVED
```

The winner maximizes:

```text
search_adjusted_margin_ppm =
    regularized_improvement_ppm
    - effective_min_regularized_improvement_ppm
```

A new reservation anywhere in the same family after selection changes the exposure state and makes the old selection stale at apply time.

## Review and apply

Selection still does not mutate the graph.

```text
reserve
 -> evaluate
 -> select
 -> independent review
 -> use-time exposure revalidation
 -> apply
```

At apply time the runtime reconstructs:

- current graph;
- current dependency history;
- current structural/search policies;
- every cumulative family reservation;
- every current-context search-adjusted evaluation.

It recomputes the selection. Any change rejects the old decision.

## Authority roles

```text
HELDOUT_SEARCH_POLICY_KEEPER
HELDOUT_SEARCH_BUDGET_KEEPER
HELDOUT_SEARCH_EVALUATOR
SEARCH_BUDGET_MODEL_SELECTOR
SEARCH_BUDGET_SELECTION_REVIEWER
SEARCH_BUDGETED_STRUCTURAL_APPLIER
```

The reference core enforces:

```text
candidate proposer != budget keeper
candidate proposer != evaluator
budget keeper != evaluator
selector != reviewer
selected proposer != reviewer
```

## Scope boundary

Passing v1.16 means a structural candidate survived:

- v1.15 selection/held-out separation;
- v1.15 complexity regularization;
- finite cumulative search budget;
- multiplicity-aware improvement threshold;
- independent review;
- current-state revalidation.

It still does not establish a causal mechanism or guarantee out-of-distribution performance.

```text
SearchCorrectedImprovement != CausalityProof
RegularizedSelection != Truth
```
