# ATMAN-LATTICE v1.19 — Drift-Governed Remediation / Safe Rollback

v1.19 begins where v1.18 intentionally stops. `ATMAN-REPLICATE/1.18` can preserve a `PERSISTENT_DRIFT_SIGNAL`, but it has no authority to decide whether the system should wait, gather evidence, revise parameters, revise structure, or roll back. `ATMAN-REMEDIATE/1.19` makes that recovery choice explicit and reviewable.

## Core law

```text
PersistentDrift != AutomaticRollback
RecoveryChoice != ErasureOfFormerValidity
```

A graph that was supported by a protected v1.17 confirmation may later fail to generalize. v1.19 preserves both facts: the earlier confirmation and the later drift evidence.

## Recovery surface

One exact current `PERSISTENT_DRIFT_SIGNAL` may produce competing proposals:

```text
persistent drift
      ↓
┌───────────────┬───────────────────┬────────────────────┬─────────────────────┬───────────────┐
│               │                   │                    │                     │
HOLD       COLLECT_MORE_DATA   PARAMETER_REVISION   STRUCTURAL_REVISION   SAFE_ROLLBACK
│               │                   │                    │                     │
└───────────────┴───────────────────┴────────────────────┴─────────────────────┴───────────────┘
                                        ↓
                              independent assessment
                                        ↓
                              complete-set selection
                                        ↓
                                independent review
                                        ↓
                                  fresh apply
```

All proposals bind the same exact:

```text
replication target
persistent-drift snapshot
latest replication evaluation
confirmed revision
current graph hash/generation
pre-confirmation rollback graph hash/generation
```

## Rollback safety is a separate question

A drift signal does not imply that the prior graph is now preferable.

The strict reference rollback assessment requires:

```text
latest_regularized_improvement_ppm <= 0
```

where the latest replication window compares the currently confirmed graph against its exact pre-confirmation base graph.

Therefore a performance-only drift can coexist with a still-positive structural advantage:

```text
confirmed model is worse than it used to be
BUT
confirmed model is still better than base
```

That condition does **not** support `SAFE_ROLLBACK` in the strict profile.

```text
Drift != EvidenceForRollback
PerformanceDrift != RollbackJustification
```

## Downstream revision paths do not bypass existing governance

`PARAMETER_REVISION` and `STRUCTURAL_REVISION` are routing decisions, not emergency mutation endpoints.

```text
PARAMETER_REVISION
    ↓
DOWNSTREAM_GOVERNANCE_REQUIRED
    ↓
ATMAN-REVISION/1.13
```

```text
STRUCTURAL_REVISION
    ↓
DOWNSTREAM_GOVERNANCE_REQUIRED
    ↓
ATMAN-GRAPH/1.14
```

The downstream protocol must still create and verify its own proposal/replay/review/apply chain.

```text
RemediationApproval != RevisionApproval
```

## Safe rollback moves forward in history

v1.19 never rewinds a graph generation.

If v1.17 produced:

```text
Graph 7
  ↓ confirmed structural revision
Graph 8
```

and later v1.18 records persistent drift, a supported rollback becomes:

```text
Graph 8
  ↓ v1.19 FORWARD_ROLLBACK
Graph 9
```

`Graph 9` copies the topology of `Graph 7`, but it is **not** `Graph 7`. It receives a new evidence-state hash binding:

```text
target
persistent-drift snapshot
proposal
assessment
selection
review
former confirmed graph
rollback-source graph
```

Thus:

```text
ForwardRollback != HistoryRewrite
```

The repository can still prove that Graph 8 was once confirmed, later drifted, and was subsequently replaced by Graph 9.

## Complete competing-set selection

The runtime gathers every remediation proposal currently registered for the exact snapshot and requires one assessment for each before selection. The selection receipt binds the complete proposal and assessment sets.

A proposal created after an old selection changes the candidate set and stales that selection at review/apply time.

Likewise, any new v1.18 replication evaluation changes the replication series and stales the old remediation snapshot.

```text
OldRecoveryChoice != CurrentRecoveryAuthority
```

## One remediation execution per snapshot

Discussion may preserve many alternatives, but one exact persistent-drift snapshot gets at most one executed remediation decision in the reference runtime.

A future `COLLECT_MORE_DATA` decision can lead to a new replication epoch and therefore a new snapshot, on which a new remediation decision may be made.

## Authority separation

`ATMAN-REMEDIATE/1.19` adds:

```text
REMEDIATION_POLICY_KEEPER
REMEDIATION_PROPOSER
REMEDIATION_ASSESSOR
REMEDIATION_SELECTOR
REMEDIATION_REVIEWER
REMEDIATION_APPLIER
```

Core separation:

```text
proposer != assessor
latest replication evaluator != assessor
selected proposer != selector
selected assessor != selector
proposer / assessor / selector != reviewer
proposer / assessor / selector / reviewer != applier
```

## Runtime protocol

Worker:

```bash
python -m model.remediation_worker
```

Protocol:

```text
ATMAN-REMEDIATE/1.19
```

Operations:

```text
register_remediation_policy
register_remediation_proposal
assess_remediation_proposal
select_remediation
record_remediation_review
apply_remediation
get_remediation_state
```

The SQLite reference runtime uses `BEGIN IMMEDIATE` for writes and stores proposals, assessments, selections, reviews, old/new graph states, and execution receipts separately.

## Epistemic boundary

v1.19 does not determine the real-world cause of drift. A `STRUCTURAL`, `PERFORMANCE`, or `BOTH` label is a score-derived classification under the bound replication policy.

```text
DriftKind != DriftCause
Remediation != CausalityProof
```

`SAFE_ROLLBACK` means only that the strict recovery policy found the pre-confirmation topology no worse on the latest bound replication comparison and that the full remediation governance chain approved a forward revision.
