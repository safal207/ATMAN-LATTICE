# v1.3 — Multiverse Semantics

v1.3 formalizes a distinction that planning systems often blur: a possible future is not yet part of history, and multiple valid histories are not automatically compatible with one another.

The names are inspired by science-fiction multiverse stories, but the protocol is an engineering model for agent planning, branch execution, checkpoint recovery, and reconciliation. It makes no claim that fictional quantum or multiverse mechanics describe physical reality.

## 1. Potentiality is not history

A `PotentialBranch` records a contemplated future against one exact source receipt:

```text
committed source
      |
      +-- Potential A
      +-- Potential B
      +-- Potential C
```

None of A/B/C is committed lineage merely because it was considered.

Only an explicit `BranchCommitReceipt` may turn one potential into a new cryptographic lineage:

```text
Potential B
     |
 explicit commit
     v
Committed Branch B
```

The committed payload must equal the payload digest that was originally proposed. A plan cannot receive approval as one future and then silently commit a different future.

## 2. Plurality is not incoherence

Two branches may both be individually valid:

```text
Valid(left) = true
Valid(right) = true
```

This does not prove either of the following:

```text
Coexist(left, right) = true
Merge(left, right)   = valid
```

v1.3 therefore introduces `IncursionReceipt`, an explicit compatibility statement over two exact branch heads.

The verdict is one of:

```text
COEXIST
INCOMPATIBLE
```

If branches coexist, no destructive resolution is invented. If they are incompatible, the receipt must name an explicit resolution mode:

```text
ISOLATE
FORK
RECONCILE
MERGE
REJECT
COMPENSATE
```

`NONE` is invalid for an incompatible pair.

## 3. Composition must preserve narrative ancestry

A merged result is not allowed to erase the fact that both parent histories existed.

`CompositeRealityReceipt` binds:

```text
left head
left lineage root
right head
right lineage root
incursion receipt
merge receipt
new target genesis
new target lineage root
```

The verifier checks the receipt against the actual parent receipts and the actual `MergeReceipt`; simply rehashing a forged composite envelope is not enough to rewrite ancestry.

The rule is:

```text
Composite(target)
    => exact left parent preserved
    => exact right parent preserved
    => merge provenance preserved
    => target has a distinct lineage root
```

## 4. Keeper is not sovereign

A coherence keeper may preserve, classify, isolate, or route histories according to explicit policy. That does not grant authority to rewrite their ancestry.

In other words:

```text
Preserve(worlds) != AuthorityToRewrite(worlds)
```

This is the anti-sovereign boundary of v1.3.

## 5. Why this matters for agents

The same failure modes appear without any fictional multiverse:

- an agent considers several tool plans and later claims an unexecuted plan happened;
- a planner approves payload A but executor commits payload B;
- two valid memory/checkpoint branches both mutate an exclusive external resource;
- a reconciliation process creates a clean summary but deletes evidence of one parent history;
- an orchestrator treats capacity limits as proof that excess branches are invalid.

v1.3 gives each of these states a distinct representation instead of collapsing possibility, history, compatibility, and composition into one boolean.

## Reference flow

```text
Committed State
      |
      +---- Potential A
      +---- Potential B
      +---- Potential C
              |
           COMMIT
              v
        Branch B (history)
              |
        compatibility check
         /            \
   COEXIST        INCOMPATIBLE
                      |
             explicit resolution
                      |
                 reconciliation
                      v
             Composite Reality
                      |
             parent ancestry kept
```
