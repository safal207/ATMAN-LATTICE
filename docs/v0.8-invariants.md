# ATMAN-LATTICE v0.8 — Additional Authority Invariants

These invariants extend the v0.7 set.

## I-40 — Authenticity Is Not Authority

> A cryptographically valid signature does not by itself prove that the signer was permitted to perform the signed role.

For signer proof `P` and grant `G`:

```text
VerifySignature(P) = true
```

is necessary but insufficient. We also require:

```text
P.role in G.roles
P.scope in G.scopes
```

Therefore:

```text
ValidSignature != ValidAuthority
```

## I-41 — Exact Signer-Key Binding

> Authority is granted to one exact subject/key pair, not to any key claiming the same human-readable identity.

A valid proof must bind to the same:

```text
subject_ref
key_id
public_key
grant_hash
```

that were authorized by the trusted issuer.

## I-42 — Authority Scope Confinement

> A role granted for one scope must not silently authorize actions outside that scope.

For exact-match v0.8 semantics:

```text
proof.scope in grant.scopes
```

must hold. A correct signature over an out-of-scope action is rejected.

## I-43 — Authority Policy Freshness

> A historically valid authority grant is not automatically current authority after the governing policy generation changes.

```text
grant.policy_generation == current_policy_generation
proof.policy_generation == current_policy_generation
```

must both hold at verification time.

Thus:

```text
Historical authority proof != Current authority
```

## I-44 — Authority Time-Bound Validity

> Authority must be evaluated against an explicit grant validity window.

For use-time `t`:

```text
grant.valid_from <= t <= grant.valid_until
```

A proof remains historical evidence after expiry but no longer constitutes current permission.

## I-45 — Exact Action Binding

> An authority proof authorizes one exact committed action, not merely an actor or role in the abstract.

```text
proof.action_digest = H(canonical(action))
```

Substituting the target action after signing must fail even when signer, role, scope, and policy generation remain unchanged.

## v0.8 acceptance additions

An authority-sensitive operation is provisionally admissible only when:

```text
trusted_issuer             = true
grant_signature            = valid
grant_hash                 = valid
subject_key_binding        = exact
role                       = authorized
scope                      = authorized
policy_generation          = current
grant_time_window          = active
action_digest              = exact
action_signature           = valid
```

The principal v0.8 counterexample is:

```text
signature_valid = true
role_authorized = false
=> REJECT
```

because possession of a signing key is not equivalent to possession of unlimited authority.
