# ATMAN-REPLICATE/1.18 — Temporal / External Replication & Confirmation Drift

v1.18 adds a post-confirmation monitoring plane after `ATMAN-CONFIRM/1.17`.

Its purpose is to answer a different question from final confirmation:

> Does the exact structure that was confirmed at time `t` continue to generalize on genuinely fresh evidence collected later, from another declared source/environment, or both?

```text
v1.17 CONFIRMED graph revision
        |
        v
ReplicationTargetReceipt
        |
        +--------------------------+
        |                          |
   TEMPORAL                   EXTERNAL
        |                          |
        +------------+-------------+
                     v
           TEMPORAL_EXTERNAL
                     |
             fresh replication batch
                     |
             frozen-model scoring
                     |
        REPLICATED / DRIFT_SIGNAL
                     |
             independent review
                     |
            replication series
                     |
      PERSISTENT_DRIFT_SIGNAL
```

## A replication target is frozen history

`ReplicationTargetReceipt` binds one exact successfully applied v1.17 chain:

```text
confirmed revision hash
candidate hash
confirmed graph hash + generation
confirmation evaluation hash
confirmation review hash
confirmation batch hash + source
baseline confirmed-model Brier score
baseline regularized structural improvement
```

The target is created from an already `CONFIRMED` and independently `APPROVE`d v1.17 result.

Replication never rewrites that baseline.

```text
ReplicationTarget != MutableCurrentEstimate
HistoricalBaseline != RecomputedBaseline
```

## Temporal replication

A temporal replication batch must begin after the original confirmation and respect the explicit policy gap:

```text
collected_from - confirmation_evaluated_at >= min_temporal_gap
```

Later batches form a strict generation lineage:

```text
R0 -> R1 -> R2 -> ...
```

with non-overlapping collection windows.

A renamed window or a second evaluation of the same evidence is not a new temporal replication.

```text
NewTimestampLabel != NewTemporalEvidence
RepeatedWindow != NewEpoch
```

## External replication

`EXTERNAL` and `TEMPORAL_EXTERNAL` batches require a `source_ref` different from the source used by the original v1.17 confirmation batch.

This prevents an internal rerun from being labeled external.

It does **not** prove institutional, causal, or statistical independence of two sources.

```text
DifferentSourceRef != ProvenIndependence
ExternalReplication != OntologicalIndependence
```

Production deployments should strengthen this reference contract with source authentication, signed dataset manifests, custody/provenance controls, and independent operators where external replication claims matter.

## Freshness remains provenance-based

Replication evidence must be disjoint from:

- search/discovery history;
- protected v1.17 confirmation batches;
- all earlier replication batches for the same target.

Freshness is checked by:

```text
sample_hash
resolution_hash
left_evidence_hash
right_evidence_hash
```

Therefore a new object wrapper does not make old reality fresh.

```text
NewSampleHash != FreshProvenance
NewDerivation != NewEvidenceSource
ReusedResolution != Replication
```

## Replication does not retrain

The confirmed structure is scored using the exact original candidate selection/training sample hashes.

Replication samples are score-only.

```text
Replication != Retraining
ReplicationData != TrainingData
```

This is necessary for drift to remain visible. If replication data were immediately folded into fitting, the observer could erase the very performance change it is trying to measure.

## Drift dimensions

The reference implementation checks two distinct forms of drift.

### Structural drift

The confirmed graph no longer beats its original base graph by more than the replication policy threshold:

```text
regularized_improvement <= min_regularized_improvement
```

### Performance drift

The confirmed model's replication Brier score becomes worse than its v1.17 confirmation baseline by more than the allowed degradation:

```text
replication_confirmed_brier - baseline_confirmation_brier
    > max_proposed_brier_degradation
```

The resulting `drift_kind` is one of:

```text
NONE
STRUCTURAL
PERFORMANCE
BOTH
```

and evaluation status is:

```text
INSUFFICIENT_REPLICATION
REPLICATED
DRIFT_SIGNAL
```

`DRIFT_SIGNAL` means the frozen confirmed model no longer satisfies the bound monitoring policy on that fresh replication batch.

It is not automatic falsification, rollback, or causal explanation.

```text
DriftSignal != ModelFalsehood
DriftSignal != RollbackAuthority
DriftSignal != DriftCause
```

## Persistent drift

Acknowledged replication evaluations can be summarized into a `ReplicationSeriesSnapshot`.

The snapshot preserves exact evaluation and review hashes, counts stable/drift observations, and tracks consecutive drift epochs.

Once:

```text
consecutive_drift_count >= persistent_drift_epochs
```

it emits:

```text
PERSISTENT_DRIFT_SIGNAL
```

Again, this is a durable signal for later governance, not an automatic mutation.

## Current-model binding

A replication target may be evaluated by the runtime only while its `confirmed_graph_hash` is still the current graph for that subject.

If a later governed revision changes the current graph, the old target remains historical evidence but no longer describes current model status.

```text
HistoricalReplicationTarget != CurrentModelStatus
OldConfirmedGraph != CurrentReplicationAuthority
```

A new confirmed graph should receive its own new replication target.

## Authority separation

v1.18 adds:

```text
REPLICATION_POLICY_KEEPER
REPLICATION_TARGET_KEEPER
REPLICATION_BATCH_KEEPER
REPLICATION_EVALUATOR
REPLICATION_REVIEWER
REPLICATION_MONITOR_KEEPER
```

Core and runtime separations include:

```text
replication batch keeper != original candidate proposer
replication batch keeper != original confirmation evaluator
replication evaluator != replication batch keeper
replication evaluator != original candidate proposer
replication evaluator != original confirmation evaluator
replication reviewer != replication batch keeper / evaluator
```

No v1.18 role has graph mutation authority.

## Durable state

SQLite preserves separately:

```text
replication policy
frozen replication target
replication batch lineage + sample JSON
replication evaluations + case hashes
replication reviews
replication series snapshots
```

Mutating protocol operations run under `BEGIN IMMEDIATE` in the reference runtime.

## Scope boundary

The reference implementation is an engineering framework for traceable temporal/external replication and drift monitoring.

It is not:

- proof of causal transportability;
- proof that sources are truly independent;
- a formal domain-adaptation theorem;
- automatic rollback governance;
- a replacement for preregistered scientific replication protocols where those are required.

```text
REPLICATED != PermanentGeneralization
ExternalReplication != UniversalValidity
Confirmed_t != Confirmed_t+1
```
