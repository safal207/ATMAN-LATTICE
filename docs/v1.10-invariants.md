# v1.10 invariants — Bayesian Evidence Loop

## I-161 — Completion Is Not Bayesian Evidence

A `VerificationCompletionReceipt` does not directly mutate hypothesis probability.

```text
Completion != EvidenceInterpretation
```

## I-162 — Interpretation Rule Precommitment

The completion-to-outcome mapping must be committed before the referenced verification completes.

```text
Rule.registered_at <= Completion.completed_at
```

A result cannot choose its own convenient interpretation after it is known.

## I-163 — Exact Completion Binding

An `EvidenceInterpretationReceipt` commits the exact `completion_hash` and work hash.

A valid interpretation for one completion is not evidence for another completion.

## I-164 — Exact Likelihood Binding

An interpretation rule and interpretation receipt bind the exact likelihood-model hash.

```text
Rule(L1) != Rule(L2)
```

## I-165 — Bayesian Update Exactness

A posterior update commits the exact prior hypothesis, interpretation, likelihood model, posterior hypothesis, probability transition, evidence state, runtime time, and updater identity.

## I-166 — Posterior Generation Advance

Every accepted Bayesian knowledge transition advances the hypothesis generation exactly once.

```text
posterior.generation = prior.generation + 1
```

## I-167 — Evidence State Continuity

The posterior evidence-state digest commits the prior evidence state plus the exact new completion, interpretation, likelihood model, and outcome.

New evidence cannot silently erase earlier evidence lineage.

## I-168 — Inconclusive Is Evidence Without Probability Shift

`INCONCLUSIVE` preserves the probability but still advances evidence state and generation.

```text
P_after = P_before
```

does not imply:

```text
EvidenceState_after = EvidenceState_before
```

## I-169 — Impossible Observation Rejection

If the declared prior and likelihood model assign zero probability to the observed outcome, the runtime rejects the update instead of manufacturing a normalized posterior.

## I-170 — Exact Cohort Knowledge Propagation

When a prior advances, every stored candidate still referencing the exact same hypothesis hash advances atomically to the same posterior.

Candidates on another hypothesis hash are not rewritten.

## I-171 — Likelihood Rebase Is Not Re-estimation

A freshness rebase preserves conditional test characteristics while changing only the bound hypothesis hash and advancing model generation.

```text
LikelihoodRebase != LikelihoodReEstimation
```

## I-172 — Observation Reuse Forbidden

A successful verification completion may produce at most one committed interpretation, and an exact prior hypothesis may be advanced at most once by the Bayesian runtime history.

```text
OneCompletion != InfiniteEvidence
```

## I-173 — Stale Bayesian State Cannot Commit

Application requires the same exact candidate, completion, prior, likelihood, rule, cohort, and cohort-model state observed by the preview.

Any intervening change invalidates the old preview.

```text
OldKnowledgePreview != CurrentUpdateAuthority
```

## I-174 — Interpretation Authority Is Not Update Authority

The ability to precommit result semantics does not imply the ability to advance the knowledge state.

```text
BAYESIAN_INTERPRETATION_RULE_KEEPER != BAYESIAN_UPDATE_KEEPER
```

## I-175 — Posterior Is Not Truth

A posterior probability is an explicit model state conditioned on a prior, likelihood model, interpretation rule, and evidence.

```text
Posterior != Truth
HighProbability != VerifiedFact
```

## I-176 — Closed Learning Loop Does Not Bypass Verification

The Bayesian plane consumes completed verification evidence and recalculates active-selection state. It does not create verification completions or A4 PASS by itself.

```text
Selection -> Verification -> Evidence -> Posterior -> Selection
```

is a learning loop, not an authorization or truth shortcut.
