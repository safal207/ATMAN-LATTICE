# v1.10 — Bayesian Evidence Loop

v1.10 closes the active-verification learning loop without collapsing verification results, evidence interpretation, probability, and truth into one concept.

```text
Active plan
   |
selected verification work
   |
ATMAN-VERIFY/1.7
   |
VerificationCompletionReceipt
PASS / HOLD / FAIL
   |
precommitted interpretation rule
   |
EvidenceInterpretationReceipt
POSITIVE / NEGATIVE / INCONCLUSIVE
   |
Bayesian update
   |
new HypothesisState
   |
likelihood freshness rebind
   |
ATMAN-ACTIVE/1.9 recalculation
   |
next question
```

Protocol: `ATMAN-BAYES/1.10`.

The reference worker is:

```bash
python -m model.bayes_worker
```

## Completion is not Bayesian evidence by itself

A verification completion reports the verifier's result. A likelihood model describes a test outcome model. Those two semantic spaces are not assumed to be identical.

For example, for one hypothesis:

```text
PASS -> POSITIVE
HOLD -> INCONCLUSIVE
FAIL -> NEGATIVE
```

may be appropriate. Another test could legitimately use a different mapping.

Therefore v1.10 requires an `EvidenceInterpretationRule` bound to the exact candidate and exact likelihood model.

```text
Completion != EvidenceInterpretation
```

## Interpretation must be precommitted

The interpretation rule must exist before the referenced verification completes.

The runtime rejects a rule registered after `VerificationCompletionReceipt.completed_at` and refuses to register a new rule after completion is already present.

This prevents hindsight mapping such as:

```text
observe FAIL
then decide that FAIL means POSITIVE
```

unless that mapping was committed before the result was known.

```text
ObservedResult -> choose convenient semantics   X
CommittedSemantics -> observe result            OK
```

## Exact likelihood binding

An interpretation rule binds `likelihood_model_hash`, not merely a human-readable model name.

If the likelihood model changes, the old interpretation rule cannot silently interpret the new model.

```text
Rule(L1) != Rule(L2)
```

## Bayesian update

For a binary hypothesis with prior probability `p`, sensitivity `s = P(+|H)`, and false-positive probability `f = P(+|not H)`:

Positive observation:

```text
P(H|+) = p*s / (p*s + (1-p)*f)
```

Negative observation:

```text
P(H|-) = p*(1-s) / (p*(1-s) + (1-p)*(1-f))
```

`INCONCLUSIVE` preserves the probability but still advances the evidence state and hypothesis generation because a verification event occurred and was interpreted.

An observation with zero probability under the declared likelihood model is rejected rather than normalized into an invented posterior.

## Evidence-state continuity

A posterior commits the exact prior evidence state, completion, interpretation, likelihood model, and interpreted outcome into a new evidence-state digest.

```text
EvidenceState N
   + exact completion
   + exact interpretation
   + exact likelihood
   -> EvidenceState N+1
```

So a numerically identical posterior probability does not erase the fact that new evidence was observed.

## Cohort propagation

`HypothesisState` is candidate-independent: multiple verification candidates may share the exact same hypothesis hash.

When one completed verification advances that prior, the runtime atomically advances every stored active-hypothesis row that still points to the exact same prior hash.

```text
Candidate A --\
Candidate B ----> Hypothesis H(N)
Candidate C --/

A completes
   |
H(N) -> H(N+1)
   |
B and C now reference H(N+1)
```

Only the exact cohort is advanced. A candidate already based on another hypothesis hash is not rewritten.

## Likelihood freshness rebind

v1.9 binds a likelihood model to an exact hypothesis hash for freshness.

After a posterior update, v1.10 mechanically rebinds current cohort likelihood models to the new hypothesis hash while preserving:

- `P(+|H)`;
- `P(+|not H)`;
- model reference;
- all other conditional test characteristics.

The model generation advances exactly once and a `LikelihoodRebaseReceipt` preserves old/new model hashes.

This is **not** a re-estimation of test quality. It only states that the same conditional test model is being evaluated against a fresher prior. If test characteristics themselves changed, the model keeper must replace them explicitly.

```text
LikelihoodRebase != LikelihoodReEstimation
```

## Closed-loop active verification

The Bayesian apply transaction performs:

```text
BEGIN IMMEDIATE
  load exact completion
  load exact prior
  load exact likelihood
  load precommitted rule
  build interpretation
  derive posterior
  verify exact update authority
  advance exact hypothesis cohort
  rebind cohort likelihood models
  append interpretation/update/rebase history
  recalculate ATMAN-ACTIVE plan
COMMIT
```

The response includes the next active state, next plan, and next expected-information-gain receipts.

This closes:

```text
uncertainty
 -> question
 -> selection
 -> verification
 -> observation
 -> posterior
 -> new uncertainty
 -> next question
```

## Stale-state rejection

A Bayesian preview binds:

- candidate;
- exact completion hash;
- exact prior hypothesis hash;
- exact likelihood model hash;
- exact interpretation rule hash;
- exact hypothesis cohort;
- exact cohort model hashes.

If any of those change between preview and application:

```text
preview B0
knowledge/model state -> B1
apply(B0)
    X
```

The runtime rejects the stale state.

## One observation, one knowledge transition

The history store makes `completion_hash` unique for interpretation and `prior_hypothesis_hash` unique for advancement.

A successful completed verification cannot be replayed to advance the same knowledge state repeatedly.

```text
OneCompletion != InfiniteEvidence
```

## Authority separation

Two roles are introduced:

```text
BAYESIAN_INTERPRETATION_RULE_KEEPER
BAYESIAN_UPDATE_KEEPER
```

The first can precommit how a verification result maps into the binary likelihood outcome space.

The second can apply an exact current posterior transition.

Neither role follows automatically from verification execution, active-plan selection, or ordinary action execution.

## Epistemic boundary

A posterior is a model state conditioned on explicit assumptions and evidence. It is not an ontological truth claim.

```text
Posterior != Truth
HighProbability != VerifiedFact
```

The quality of the posterior depends on the quality and calibration of the prior, likelihood model, interpretation rule, and underlying verification evidence.

v1.10 is a reference Bayesian evidence-accounting plane, not a claim that all agent uncertainty is binary or that Bayesian updating is sufficient for every epistemic problem.
