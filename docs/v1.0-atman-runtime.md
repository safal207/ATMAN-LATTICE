# ATMAN Runtime v1.0

ATMAN Runtime v1.0 moves the A1/A2/A3/A4 observer plane behind a separate process boundary.

## Goal

v0.9 established a governed in-process API: authority is checked before a privileged primitive is called. v1.0 strengthens that architecture by making the reference privileged observer plane execute in a fresh Python process through a JSON protocol.

The boundary is intentionally narrow:

```text
client process
    |
    | ATMAN-RUNTIME/1.0 JSON request
    | grant + proof + operation inputs
    v
runtime worker process
    |
    +-- server-owned trusted roots
    +-- server-owned policy generation
    +-- server-owned verification time
    |
    v
authority enforcement
    |
    v
A1 / A2 / A3 / A4 primitive
    |
    v
ObserverReceipt JSON response
```

## Supported privileged operations

The v1.0 process worker exposes:

- `observe_space` -> `A1_OBSERVER`
- `observe_time` -> `A2_OBSERVER`
- `cross_axis_bind` -> `A3_BINDER`
- `global_coherence` -> `A4_KEEPER`

Token issuance/revocation and merge remain governed in-process adapters in v1.0 and are candidates for later runtime expansion.

## Server-owned trust

The request is not allowed to define the trusted root set, current policy generation, or runtime verification clock. The reference worker obtains those from its own environment:

```text
ATMAN_TRUSTED_ISSUER_KEYS
ATMAN_POLICY_GENERATION
ATMAN_RUNTIME_NOW
```

The environment mechanism is only the reference configuration channel. A deployed service should source these values from service-owned configuration or a protected control plane.

A request that includes fields named `trusted_issuer_keys` or `policy_generation` does not override the worker configuration.

## Protocol

Each request contains:

```json
{
  "protocol": "ATMAN-RUNTIME/1.0",
  "request_id": "...",
  "operation": "observe_space",
  "payload": {},
  "grant": {},
  "proof": {}
}
```

The runtime reconstructs the exact canonical action from the decoded operation inputs through the v0.9 governed adapter. It does not trust a client-provided action description.

Successful response:

```json
{
  "protocol": "ATMAN-RUNTIME/1.0",
  "request_id": "...",
  "ok": true,
  "receipt": {}
}
```

Rejected response:

```json
{
  "protocol": "ATMAN-RUNTIME/1.0",
  "ok": false,
  "error_type": "PermissionError",
  "error": "..."
}
```

A rejected request does not return an observer receipt.

## Process-isolation regression

The test suite monkeypatches the client process copy of `model.enforcement.governed_observe_space` with a function that raises immediately. It then invokes `python -m model.runtime_worker` in a fresh interpreter.

The authorized runtime request still succeeds because the worker imports and executes its own code in another process. This proves that ordinary client-process mutation does not alter the worker implementation.

## What v1.0 does not claim

This is a reference process boundary, not a complete hostile-host sandbox.

If an attacker controls the runtime host, service account, worker package, environment, or trusted-root configuration, the security boundary can be replaced or subverted. Production deployments still require operating-system/container isolation, protected service identity, authenticated transport, protected configuration, and durable audit storage appropriate to the threat model.

The precise claim is:

> When callers interact through the ATMAN Runtime service boundary and do not control the worker process or its trust configuration, privileged observer execution is gated by server-side authority verification and cannot be bypassed by mutating the caller process.

## Core rule

```text
client permission claim
        !=
server execution authority
```

A privileged state transition exists only after the runtime process independently accepts the exact grant, signer, role, scope, action, policy generation, and validity interval.
