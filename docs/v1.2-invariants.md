# v1.2 Additional Invariants — Trust Governance

## I-67 — Governance Plane Separation

Ordinary execution authority is not sufficient evidence for trust-root mutation.

```text
AuthorityGrant != TrustPolicyTransitionAuthority
```

Trust changes use `ATMAN-TRUST/1.2`, separate from `ATMAN-RUNTIME/1.1`.

## I-68 — Current-Policy Quorum

A trust transition is valid only when distinct currently trusted roots satisfy the threshold of the current policy.

```text
valid_transition => unique_valid_current_root_signatures >= current.threshold
```

The proposed next threshold cannot weaken the quorum required to activate itself.

## I-69 — Exact Transition Binding

Each trust approval binds the signer to the exact current policy and exact transition digest.

```text
approval -> current_policy_hash × next_roots × next_threshold × reason × transition_time
```

Changing any bound field invalidates reuse of the approval.

## I-70 — Trust Generation Monotonicity

Every successful transition advances exactly one generation.

```text
G_next = G_current + 1
```

No same-generation replacement and no generation skip is accepted by the reference transition model.

## I-71 — Trust History Continuity

Every non-bootstrap policy points to the exact policy it replaced.

```text
Policy(N+1).previous_policy_hash = hash(Policy(N))
```

Root rotation changes authority while preserving a verifiable governance lineage.

## I-72 — Bootstrap Is Not Ongoing Authority

Bootstrap environment roots initialize an empty runtime database only once.

After persisted trust state exists:

```text
persisted_policy > bootstrap_environment
```

A restart with stale bootstrap configuration must not roll authority backward.

## I-73 — Old Root Non-Authority After Rotation

Removal from the active root set removes eligibility to issue new grants for the new policy generation.

```text
root ∉ current_policy.roots => grants signed by root are untrusted
```

Historical signatures remain historical evidence; they do not become current authority.

## I-74 — Atomic Trust Transition

The transition check and policy write must occur against one serialized current policy state.

```text
verify Policy N + commit Policy N+1 = one atomic mutation
```

A stale transition cannot validly commit a second successor after another process already advanced the policy.

## I-75 — Governance Receipt Preservation

Every committed trust transition produces a receipt binding the exact predecessor, successor, quorum evidence, and transition reason.

```text
TrustTransitionReceipt -> from_policy × to_policy × approvals × threshold × reason × time
```

## I-76 — Quorum Compromise Boundary

The reference security claim is bounded by root-key custody.

If an attacker controls enough current private root keys to satisfy `current.threshold`, the cryptographic quorum condition is satisfied. v1.2 does not claim to distinguish legitimate governance from a threshold-level key compromise.
