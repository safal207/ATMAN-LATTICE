# ATMAN-LATTICE v0.7 — Additional Consumption Invariants

These invariants extend the v0.6 set.

## I-34 — One-Time Authorization Consumption

> A specific authenticated `UseToken` may authorize at most one successful consumption event.

Let `D(T)` be the stable digest of an exact token and `L` the authoritative authorization ledger.

After:

```text
CONSUMED(D(T)) ∈ L
```

any later attempt to consume `T` must fail.

Thus:

\[
Count_L(CONSUMED(D(T))) \le 1.
\]

## I-35 — Revocation Dominates Future Use

> Once an exact token has been revoked, that token must not authorize a later action even if its cryptographic MAC and expiry window would otherwise still be valid.

```text
REVOKED(D(T)) ∈ L
=> consume(T) = REJECT
```

Revocation changes authorization status; it does not rewrite the historical validity of the token at issuance time.

## I-36 — Consumption Is Historically Irreversible

> Revocation after a token has already been consumed must not retroactively redefine the completed consumption as if it never occurred.

```text
CONSUMED(D(T))
then REVOKE(T)
=> REJECT revocation as a terminal replacement
```

If a completed action must be reversed, that requires a separate compensating-action protocol rather than mutation of authorization history.

## I-37 — Authorization Ledger Lineage

> Consumption and revocation events must form one inspectable append-only lineage.

For adjacent authorization events:

\[
E_n.previous\_event\_hash = H(E_{n-1}).
\]

The ledger head and generation must agree with the event sequence, and authenticated event content must remain tamper-evident.

## I-38 — Terminal Event Uniqueness

> An exact token digest may have zero or one terminal authorization event, never multiple competing terminal histories inside one valid ledger.

Invalid examples include:

```text
CONSUMED(T), CONSUMED(T)
REVOKED(T), CONSUMED(T)
CONSUMED(T), REVOKED(T)
```

A ledger containing such duplicate terminal events is invalid even if each individual event is otherwise well-formed.

## I-39 — Current-Ledger Append Binding

> A consumption or revocation append is valid only against the ledger generation the caller actually verified.

```text
expected_ledger_generation == current_ledger_generation
```

If the authoritative ledger has advanced, the append must be retried from fresh state rather than silently composed onto a stale snapshot.

For distributed implementations, this equality must be enforced atomically by the authoritative store.

## v0.7 acceptance additions

A use is provisionally admissible only when:

```text
use_token_authentication = valid
use_token_context = current
use_token_expiry = valid
authorization_ledger = valid
token_terminal_event = absent
ledger_generation_binding = current
consumption_event_authentication = valid
consumption_event_parent_link = valid
```

A revocation is provisionally admissible when:

```text
exact_use_token_authentication = valid
authorization_ledger = valid
token_terminal_event = absent
ledger_generation_binding = current
revocation_event_authentication = valid
revocation_event_parent_link = valid
```

The principal v0.7 counterexample is:

```text
UseToken = cryptographically valid
UseToken = unexpired
context = unchanged
BUT
CONSUMED(token_digest) already exists
=> REJECT
```

This separates **authorization validity** from **authorization availability**.
