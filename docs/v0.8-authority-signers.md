# ATMAN-LATTICE v0.8 — Authority / Signer Identity

Version 0.8 separates two questions that earlier versions intentionally left coupled:

1. **Is this artifact cryptographically authentic?**
2. **Was this signer authorized to perform this role, for this scope, under the current policy generation?**

A valid signature answers only the first question.

## Protocol shape

```text
Trusted root public key
        |
        | Ed25519 signs
        v
AuthorityGrant
  subject_ref
  subject public key
  roles[]
  scopes[]
  policy_generation
  validity window
        |
        | exact grant_hash
        v
AuthorityProof
  role
  scope
  action_digest
  policy_generation
  signed_at
  Ed25519 signature
        |
        v
use-time authority verification
```

The trusted root set is an explicit trust boundary supplied by the caller. ATMAN-LATTICE does not claim that a key becomes authoritative merely by existing or by being able to produce a valid signature.

## Ed25519 signer identity

`model/authority.py` uses Ed25519 asymmetric signatures for grants and action proofs.

A grant binds one exact public key to:

```text
subject_ref
key_id
roles
scopes
policy_generation
valid_from / valid_until
issuer identity
```

The issuer signs the canonical grant material. The signed grant is then committed by `grant_hash`.

An authorized actor signs exact action material committed by:

```text
action_digest = SHA256(canonical(action))
```

The resulting `AuthorityProof` is bound to the exact grant hash, role, scope, policy generation, and signing time.

## Core counterexample

```text
signature_valid = true
role = USE_TOKEN_ISSUER

grant.roles = [A4_KEEPER, USE_TOKEN_REVOKER]

=> REJECT(role_not_authorized)
```

Therefore:

> **Cryptographic authenticity is necessary but not sufficient for authority.**

The same applies to scope:

```text
signature_valid = true
scope = authorization:agent:2

grant.scopes = [authorization:agent:1]

=> REJECT(scope_not_authorized)
```

## Policy generation

Authority is use-time state, not a permanent property of a key.

If a grant was issued under policy generation `N` and the current policy generation is `N+1`, the old grant remains historically authentic but is no longer current authority:

```text
valid old signature
+ stale policy generation
=> REJECT
```

This deliberately mirrors v0.4 freshness semantics:

```text
Historical authenticity != Current authority
```

## Validity windows

A grant also has an explicit validity interval. A proof may have been correctly signed while the grant was active and still be rejected later when current authorization evaluation occurs after the grant expires.

That is intentional. The historical proof remains verifiable evidence; it is not silently promoted into current permission.

## Roles and scopes

The v0.8 model treats role and scope strings as protocol identifiers rather than hard-coding one universal policy vocabulary. Example roles include:

```text
A1_OBSERVER
A2_OBSERVER
A3_BINDER
A4_KEEPER
USE_TOKEN_ISSUER
USE_TOKEN_REVOKER
AUTHORIZATION_LEDGER_WRITER
MERGE_RECONCILER
```

Example scopes include:

```text
identity:agent:1
authorization:agent:1
branch:future/left
merge:identity:agent:1
```

Production policies may define richer hierarchical or predicate-based scopes later. v0.8 intentionally starts with exact-match scope semantics so authorization remains falsifiable and inspectable.

## Trust boundary and non-goals

v0.8 does not solve root-of-trust governance by itself. The caller supplies trusted issuer public keys. A future governance layer may define quorum, rotation, delegation chains, or transparency logs for those roots.

v0.8 also does not automatically rewrite every earlier A1/A2/A3/A4 function to require an authority proof. Instead it defines the reusable authority primitive that those execution boundaries can require in integration adapters.
