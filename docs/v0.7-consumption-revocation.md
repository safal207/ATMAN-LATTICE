# ATMAN-LATTICE v0.7 — One-Time Consumption and Revocation

Version `0.7.0` closes a gap left intentionally open by v0.4: an authentic, fresh `UseToken` was still replayable multiple times until expiry unless the surrounding system remembered that it had already been used.

The v0.7 protocol adds an append-only authorization ledger with two terminal event types:

```text
CONSUMED
REVOKED
```

For a specific exact token digest, either event permanently blocks later consumption of that same token.

## Core rule

> **A valid authorization may be used at most once, and may be revoked before use.**

A `UseToken` is first reduced to a stable digest over its exact authenticated content:

```text
UseToken
   ↓
digest_use_token(token)
   ↓
AuthorizationEvent
```

The event commits to:

```text
ledger_generation
event_type
token_digest
subject_identity_ref
branch_ref
subject_generation
lineage_root_hash
context_digest
occurred_at
actor_ref
reason_ref
previous_event_hash
key_id
mac
        ↓
    event_hash
```

Events form a hash-linked ledger:

```text
E1
 |
 v
E2.previous_event_hash = H(E1)
 |
 v
E3.previous_event_hash = H(E2)
```

Each event is also authenticated with HMAC-SHA256 in the current research harness.

## Consumption path

```text
UseToken
  ↓ verify current context + expiry + MAC
AuthorizationLedger
  ↓ verify current ledger integrity
check token has no terminal event
  ↓
expected_ledger_generation == current generation
  ↓
append CONSUMED
  ↓
new ledger generation + new head hash
```

A second consumption attempt against the updated ledger is rejected as:

```text
token_already_consumed
```

## Revocation path

Revocation targets the exact authenticated `UseToken`, not the current environment context.

That distinction is deliberate: a policy keeper must still be able to revoke a token after the world changes, because the purpose is to invalidate the already-issued capability itself.

```text
UseToken
  ↓ verify structure + MAC
AuthorizationLedger
  ↓ verify integrity
check token has no terminal event
  ↓
append REVOKED
```

Any later use attempt is rejected as:

```text
token_already_revoked
```

Revocation after consumption is also rejected. v0.7 does not pretend that a completed action can be retroactively undone by changing authorization state.

## Optimistic concurrency binding

Each append requires:

```text
expected_ledger_generation == ledger.generation
```

This detects attempts to append using an already superseded authorization snapshot.

In a real multi-process or distributed deployment, this comparison must be performed atomically by the authoritative ledger store using a transaction, compare-and-swap, conditional write, or equivalent serialization mechanism.

The pure Python research model cannot make two independent stale copies of an in-memory object mutually exclusive by itself. v0.7 therefore specifies the atomic-store requirement explicitly rather than claiming stronger concurrency guarantees than it implements.

## Why terminal events are unique

`verify_authorization_ledger()` rejects multiple terminal events for one token digest:

```text
CONSUMED(token X)
CONSUMED(token X)   -> invalid ledger
```

and likewise:

```text
REVOKED(token X)
CONSUMED(token X)   -> invalid ledger
```

The accepted history for an exact token contains zero or one terminal event.

## Security properties explored

The executable fixtures cover:

- first use succeeds;
- replay after consumption fails;
- revocation before use blocks consumption;
- consumption prevents retroactive revocation from rewriting history;
- stale ledger generation is rejected;
- event-content tamper is detected;
- use-token tamper prevents revocation as if the token were authentic;
- revocation remains possible even when the original execution context is no longer current.

## Non-goals

v0.7 does not yet provide:

- a durable database-backed atomic compare-and-swap implementation;
- distributed consensus across multiple authorization ledgers;
- asymmetric event signatures;
- revocation by identity-wide policy rather than exact token digest;
- compensating actions for already-consumed authorization;
- garbage collection or archival semantics for expired tokens.

Those are future integration layers rather than facts hidden behind the current model.
