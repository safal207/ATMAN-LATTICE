# v1.15 — Held-Out Structural Validation / Complexity-Regularized Graph Selection

v1.15 adds a stricter structural-learning gate above v1.14. A dependency graph may improve replay on the data used to discover it and still fail on data that was not used for selection.

The reference protocol is:

```text
ATMAN-STRUCTURE/1.15
```

The layer remains an engineering/statistical model. A directed edge still means `STATISTICAL_CONDITIONING`, not proven physical or causal direction.

## Core laws

```text
SelectionData != EvaluationData
BetterReplay != BetterGeneralization
MoreEdges != MoreKnowledge
HeldOutImprovement != CausalityProof
RegularizedSelection != Truth
Selected != Applied
```

## Deterministic held-out partition

A `StructuralValidationPolicy` is registered once for a subject and binds:

```text
evaluation_modulus
min_selection_samples
min_evaluation_samples
dependency_threshold_bps
edge_penalty_ppm
```

For each dependency-pair sample, the evaluation bucket is derived deterministically from its immutable `sample_hash` under the v1.15 partition domain. Bucket `0` is evaluation; all other buckets are selection.

The split has no runtime random draw and no client-supplied salt.

Every sample belongs to exactly one side:

```text
History = Selection union Evaluation
Selection intersection Evaluation = empty
```

The policy itself is immutable once registered in the reference runtime.

## Candidate construction uses selection data only

A v1.15 `StructuralValidationCandidate` contains a v1.14 structural proposal plus its v1.14 replay, but both are reconstructed from the **selection partition only**.

The candidate binds:

```text
policy hash
full dependency-history hash
split hash
selection sample hashes
evaluation sample hashes
base graph hash
proposal hash
selection replay hash
proposer
```

A candidate is admitted to held-out validation only when its selection replay is `STRUCTURE_IMPROVED`.

This is not enough for apply.

## Held-out evaluation

The held-out evaluator estimates prediction parameters from selection data and scores only evaluation cases.

For the base and proposed structure:

```text
base_mean_brier
proposed_mean_brier
raw_improvement = base_mean_brier - proposed_mean_brier
```

The reference statuses are:

```text
INSUFFICIENT_HELDOUT
HELDOUT_IMPROVED
OVERFIT_SIGNAL
COMPLEXITY_REJECTED
```

`OVERFIT_SIGNAL` means the candidate improved the selection replay but did not improve raw held-out Brier score.

```text
BetterReplay != BetterGeneralization
```

The candidate remains preserved as history; it is simply ineligible for current structural selection.

## Complexity regularization

v1.15 also scores model complexity explicitly:

```text
base_regularized_brier = base_mean_brier + edge_penalty_ppm * base_edge_count
proposed_regularized_brier = proposed_mean_brier + edge_penalty_ppm * proposed_edge_count
regularized_improvement = base_regularized_brier - proposed_regularized_brier
```

A proposal that improves raw held-out prediction but whose gain is no larger than its configured complexity cost becomes:

```text
COMPLEXITY_REJECTED
```

Therefore:

```text
MoreEdges != MoreKnowledge
```

The penalty is a policy choice, not a truth metric. Changing it changes selection preference, not historical evidence.

## Competing graph selection

`finalize_structural_selection` does not accept an arbitrary client candidate list.

The runtime automatically loads **all currently held-out-validated candidates** with the exact same:

```text
subject
pair key
base graph hash
policy hash
dependency-history hash
```

Eligible candidates must have `HELDOUT_IMPROVED`.

The winner has the largest positive `regularized_improvement_ppm`, with deterministic candidate-hash tie breaking.

If no candidate passes:

```text
NO_ELIGIBLE_CANDIDATE
```

This means only that no current candidate passed this evaluation policy.

```text
NO_ELIGIBLE_CANDIDATE != NoRealDependency
```

## New competitors invalidate an old selection

A selection receipt binds the entire candidate and validation set.

If another candidate is held-out validated after selection but before apply, the runtime recomputes the current candidate set and rejects the old selection:

```text
OldCandidateSet != CurrentSelectionAuthority
```

This prevents an earlier selection from ignoring a later competing structure.

## New evidence invalidates an old selection

The candidate, held-out validation, and selection all bind the full dependency-history hash.

If another resolved dependency-pair sample appears before apply:

```text
OldHistory != CurrentSelectionAuthority
```

A new candidate/validation/selection cycle is required.

## Independent roles

v1.15 adds:

```text
STRUCTURAL_VALIDATION_POLICY_KEEPER
STRUCTURAL_CANDIDATE_PROPOSER
HELDOUT_STRUCTURAL_VALIDATOR
STRUCTURAL_MODEL_SELECTOR
STRUCTURAL_SELECTION_REVIEWER
VALIDATED_STRUCTURAL_SELECTION_APPLIER
```

The held-out validator cannot be the candidate proposer.

The selection reviewer cannot be the selected proposer or the selector.

```text
Propose != Validate != Select != Review != Apply
```

## Apply and immutable history

Only a `HELDOUT_IMPROVED` selected candidate with an independent `APPROVE` review may pass the v1.15 apply wrapper.

At use time the runtime verifies:

- current graph still equals the selection base graph;
- current validation policy still matches;
- dependency history is unchanged;
- the complete currently validated candidate set is unchanged;
- the selected validation is still the deterministic winner;
- review and authority bindings match exactly.

Successful apply advances the v1.14 graph generation but stores a v1.15 history row containing:

```text
base graph JSON
new graph JSON
candidate
held-out validation
selection
review
validated revision receipt
```

Historical failed/overfit candidates are not deleted.

## Scope boundary

Held-out validation improves resistance to structural overfitting. It does not establish causal direction, guarantee out-of-distribution performance, or make a chosen graph ontologically true.

Production systems additionally need protected evaluation data, leakage controls, temporal or external validation where appropriate, multiple-comparison controls when searching many structures, protected policy governance, and rollback-resistant history.
