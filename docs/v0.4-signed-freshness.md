# ATMAN-LATTICE v0.4 — Signed Freshness and Use Binding

Version 0.4 adds a verification-to-use boundary on top of the v0.3 cryptographic lineage model.

The problem is temporal: a verdict can be correct when produced and unsafe when consumed later because the execution context changed.

```text
verify(context = C1) -> PASS
              time passes
context becomes C2
              ↓
execute using old PASS   <- invalid
```

ATMAN-LATTICE treats the historical observer verdict and its use-time authorization as different artifacts.

## 1. Historical verdict remains immutable

`ObserverReceipt` keeps the v0.3 result:

```text
A4 = PASS
identity / branch / generation / lineage_root
inputs / evidence / limitations
```

The receipt is not rewritten to pretend that an old verdict is fresh.

## 2. ObserverAttestation

`ObserverAttestation` authenticates an exact observer receipt under an exact execution-relevant context and verification time.

```text
ObserverReceipt
      ↓ digest
observer_receipt_digest
      +
context_digest
verified_at
key_id
      ↓
HMAC-SHA256
      ↓
ObserverAttestation
```

The prototype uses HMAC-SHA256 from the Python standard library. This is an authenticated MAC for the executable research harness, not an asymmetric public-key signature. A future version may replace the signer abstraction with Ed25519 or another public-key scheme without changing the core context/freshness invariants.

## 3. Freshness check

An attestation is usable only if all of the following remain true at verification time:

- the referenced `ObserverReceipt` digest still matches;
- identity, branch, generation, lineage root, and verdict still match the receipt;
- the current context hashes to the same `context_digest`;
- `verified_at` is not in the future;
- the attestation age is within the caller's maximum allowed age;
- the attestation key is known;
- the HMAC authenticates the exact attestation material.

A cryptographically authentic but stale attestation is therefore not accepted for use.

## 4. UseToken

A `PASS` attestation can be converted into a short-lived `UseToken`.

The token binds:

```text
subject identity
branch
generation
lineage_root_hash
observer_receipt_digest
attestation_digest
context_digest
issued_at
expires_at
key_id
```

The token is independently authenticated with HMAC-SHA256.

At the actual use boundary, `verify_use_token()` recomputes the current context digest and rejects the token if the world changed after authorization.

```text
A4 PASS
  ↓
ObserverAttestation(C1, t0)
  ↓ fresh + authentic
UseToken(C1, [t1, t_exp])
  ↓
actual use under C1 -> PASS
actual use under C2 -> FAIL(context_mismatch)
actual use after t_exp -> FAIL(token_expired)
```

## 5. TOCTOU invariant

The core rule is:

> Verification authorizes use only for the context, lineage, observer result, and bounded time window to which the authorization is cryptographically bound.

Equivalently:

```text
historical PASS != current authorization
```

A use-time check must bind back to the exact verified receipt and to the execution context that is current at use.

## 6. Executable counterexamples

The v0.4 test suite demonstrates:

1. a valid signed attestation verifies;
2. tampering with the observer receipt after attestation is detected;
3. an attestation older than its allowed age is rejected;
4. changing policy/context generation invalidates an otherwise authentic attestation;
5. a `UseToken` works only under the exact bound context;
6. an expired token is rejected;
7. mutating token fields invalidates its MAC.

## 7. Non-goals in v0.4

Version 0.4 does not yet provide:

- asymmetric public-key signatures;
- a persistent revocation registry;
- one-time token consumption / replay prevention;
- distributed clock consensus;
- external trust anchors.

Those are deliberately left explicit rather than implied by the current prototype.
