# v1.6 — Verification Pressure / Temporal Loom

v1.6 models what happens when verification demand grows faster than A3/A4 capacity.

The central rule is:

> **Unverified does not mean invalid.**

Capacity is an admission constraint over verification work, not a semantic verdict over the branch, path, or claim being verified.

## Problem

A branching agent system may produce work faster than a verifier can process it:

```text
branch / path evidence
   |   |   |   |   |   |
   v   v   v   v   v   v
        A3 / A4
     finite capacity
```

A naive system often collapses overload into one of two dangerous behaviors:

1. silently drop excess work;
2. treat unprocessed work as failed or invalid.

v1.6 forbids both.

## Work items

`VerificationWorkItem` binds:

```text
work_ref
subject_identity_ref
evidence_digest
cost_units
priority
submitted_at
work_hash
```

The object represents required verification work. It does not contain a PASS/FAIL verdict.

## Capacity policy

`VerificationCapacityPolicy` declares:

```text
capacity_units
max_admitted_items
aging_quantum
```

The scheduler ranks work deterministically by effective priority:

```text
effective_priority = priority + floor(wait_time / aging_quantum)
```

Aging prevents permanently fresh high-priority traffic from starving older work forever.

## Pressure accounting

Each offered item must appear in exactly one disposition:

```text
ADMITTED
DEFERRED_CAPACITY
DEFERRED_OVERSIZED
```

No item may silently disappear.

`VerificationPressureReceipt` records the exact offered set, deterministic rank order, admitted set, deferred sets, capacity consumption, policy hash, measurement time, and pressure status.

Pressure statuses are:

```text
NORMAL     — all offered work admitted
PRESSURED  — some work admitted and some deferred
SATURATED  — offered work exists but none can be admitted
```

`DEFERRED_OVERSIZED` means the declared work unit cannot fit even into an otherwise empty capacity window. It remains explicit evidence requiring decomposition or a larger verification budget. It is not invalidated.

## Coverage gate

Admission is still not completion.

`VerificationCoverageReceipt` separates:

```text
completed
pending_admitted
deferred
```

A base `PASS` can remain `PASS` only if every required item was both admitted and completed.

```text
all required verification complete -> base decision may survive
pending admitted work              -> HOLD
deferred required work             -> HOLD
invalid pressure evidence          -> FAIL
claiming deferred work completed   -> FAIL
base FAIL                           -> FAIL
```

Thus:

```text
Capacity shortage != semantic failure
Incomplete verification != global PASS
```

## Relation to geometric coherence

v1.5 introduced `PASS / HOLD / FAIL` for torsion and curvature evidence. v1.6 makes `HOLD` operational under pressure:

```text
A3/A4 geometric work
       |
       v
verification scheduler
       |
  +----+----------------+
  |                     |
admitted              deferred
  |                     |
pending/completed     HOLD, preserved
```

The reference v1.6 module is an executable scheduling/coverage model. It is not yet a new runtime wire protocol or distributed job queue.

## Security and systems boundary

The model assumes that declared `cost_units`, priority, and timestamps are supplied under an appropriate trusted policy boundary. A hostile caller able to assign arbitrary priorities or costs could game admission. Production integration should therefore bind workload metadata to server-owned policy, measured resource accounting, or authorized scheduler decisions.

The scheduler is deterministic for a fixed offered set, policy, and measurement time. It does not claim optimal bin packing or universal fairness. Aging is a bounded anti-starvation mechanism, not a proof that every oversized job can eventually run.
