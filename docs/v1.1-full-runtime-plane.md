# ATMAN-LATTICE v1.1 — Full Runtime Plane

v1.1 expands the v1.0 process boundary from the observer plane to the complete privileged lifecycle:

```text
observe
  ↓
issue capability
  ↓
consume / revoke
  ↓
reconcile branches
```

The wire protocol is now `ATMAN-RUNTIME/1.1`.

## Runtime-owned authority and secrets

The runtime owns and loads these values from its deployment environment rather than from request fields:

- trusted authority-root public keys;
- current authority policy generation;
- runtime verification clock;
- attestation verification keys;
- use-token signing keys;
- authorization-event signing keys;
- authorization SQLite database path.

A caller may reference an allowed `key_id`, but cannot supply the server secret used for a use token or authorization event.

## Supported privileged operations

```text
observe_space       -> A1_OBSERVER
observe_time        -> A2_OBSERVER
cross_axis_bind     -> A3_BINDER
global_coherence    -> A4_KEEPER
issue_use_token     -> USE_TOKEN_ISSUER
consume_use_token   -> USE_TOKEN_CONSUMER
revoke_use_token    -> USE_TOKEN_REVOKER
merge_branches      -> BRANCH_MERGER
```

Each operation reconstructs its exact canonical action from decoded runtime inputs and server-owned current state before verifying the authority proof.

## Atomic authorization state

v0.7 defined generation-bound authorization ledgers, but a caller-provided ledger would not be sufficient across separate processes: two processes could both receive the same stale generation.

v1.1 therefore moves terminal authorization state into a server-owned SQLite store.

For `consume_use_token` and `revoke_use_token`, the runtime executes:

```text
BEGIN IMMEDIATE
  ↓
load current ledger for identity
  ↓
reconstruct action using actual current generation
  ↓
verify exact authority proof
  ↓
verify token + terminal state
  ↓
append CONSUMED or REVOKED event
  ↓
persist new generation
COMMIT
```

Two runtime processes cannot both validate and commit against the same previous ledger generation. The first writer advances the ledger; the second observes the new generation after acquiring the database write lock.

This turns the v0.7 optimistic-concurrency contract into a concrete reference implementation using SQLite transactional serialization.

## Replay behavior

A request signed against ledger generation `N` is not valid once the server ledger has advanced to `N+1`.

Depending on which check detects the stale replay first, the runtime can reject it as an action digest mismatch, stale generation, already-consumed token, or already-revoked token. All are rejection paths; none append a second terminal event.

## Branch reconciliation

`merge_branches` now executes behind the same process boundary as observers and capability lifecycle operations. The runtime independently validates:

- exact ancestor receipt;
- left and right lineage chains;
- both restore proofs;
- conflict-resolution completeness;
- target branch and generation;
- merged payload digest;
- merge authority proof.

The resulting merge genesis and `MergeReceipt` are produced inside the privileged runtime process.

## Reference-boundary claim

v1.1 provides a process-separated reference runtime plus a server-owned transactional authorization store. It does not claim protection against an attacker who controls the runtime host, worker package, environment configuration, SQLite database file, or trusted-root configuration.

Production deployment still requires appropriate OS/container isolation, authenticated transport, file/database permissions, secret management, rollback protection, backups, and operational audit controls.

The narrow claim is:

> When callers do not control the runtime process or its protected configuration/state, privileged observer, capability lifecycle, and merge operations are mediated by server-owned authority checks and terminal authorization state.
